Architecture Reference

Certificate Flows — Intune PKI & Android KeyChain

Two sequence diagrams covering (1) how Microsoft Intune provisions an X.509 client certificate onto an enrolled Android device via SCEP, and (2) how a user selects and persists the certificate alias inside the MRZ Scanner app for later mTLS use.

1

Intune Certificate Deployment (SCEP / PKCS)

IT Admin configures a SCEP profile in Intune. The MDM agent on the enrolled device generates a private key entirely inside the Android Keystore (never exported), creates a CSR, and exchanges it with the NDES proxy. The CA signs and returns the certificate, which is stored in the device keystore — accessible to apps via KeyChain.choosePrivateKeyAlias().

TEE = Trusted Execution Environment (hardware-backed key storage on modern Android)
Private key never leaves the device — only the CSR (public key + metadata) is sent to the CA
NDES = Network Device Enrollment Service — Microsoft's SCEP proxy for AD CS
Protocol: SCEP (RFC 8894) over HTTPS. The device CSR is wrapped in CMS (Cryptographic Message Syntax / PKCS#7) and encrypted with the NDES Registration Authority certificate before transmission. The challenge password is a one-time token Intune generates and embeds in the MDM policy payload — the NDES server uses it to authorise the request without requiring AD credentials on the device. Alternative: PKCS#12 deployment (Intune encrypts the PFX with a device-specific key and delivers it via MDM) — same result in Keystore, slightly different exchange; configurable per profile in Intune.
2

In-App Certificate Alias Selection

First-launch flow: the app calls KeyChain.choosePrivateKeyAlias() which surfaces the OS certificate picker (filtered to certificates matching the API host). The selected alias is persisted in SharedPreferences. On all subsequent launches the alias is loaded silently. When a REST API call is made, the alias is passed to the native OkHttp layer which retrieves the private key and certificate chain from the Keystore to perform mutual TLS.

mTLS flow (Phase 4): the private key signing operation happens entirely inside the Android Keystore's TEE. OkHttp builds a custom javax.net.ssl.X509KeyManager whose getPrivateKey() returns the Keystore-backed PrivateKey object — Java's TLS stack calls Signature.sign() on it, which delegates to the TEE without ever exporting raw key material. The server authenticates the client by verifying the certificate chain against the Intune CA it trusts. Revocation: Intune can push an MDM command to remove the certificate; the next hasCertificate() call will return false and the app will re-prompt for selection.
